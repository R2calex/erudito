API Endpoints

Sistema
GET /health — Status, Qdrant, Ollama, NLM, Redis
GET /metrics — KPIs: cobertura, coherencia, freshness, etc.
GET /audit — Log de operaciones recientes
Registry
GET /registry — Listar todos los proyectos y su estado
GET /registry/{project} — Detalle de un proyecto
POST /registry — Registrar nuevo proyecto (name, path, node, repo)
Scanning
POST /scan — Forzar scan de todos los proyectos
POST /scan/{project} — Forzar scan de un proyecto especifico
Consultas
GET /search?q=...&project=...&top_k=5 — Busqueda semantica con confidence routing
GET /search?q=...&top_k=10 — Busqueda cross-project (sin filtro, solo Qdrant)

Migracion desde v2

1. Qdrant collection agent_knowledge: Se mantiene. Los embeddings existentes siguen siendo validos. Se agrega collection nlm_notes.
2. scan_state.json → registry.yaml: Migrar last_hash de cada source al nuevo formato del registry. Script de migracion one-shot.
3. Crear notebooks: Primer rondin post-deploy crea los notebooks en NotebookLM para cada proyecto registrado.
4. Endpoints backward-compatible: /health, /search, /scan siguen funcionando igual. Se agregan /registry y /metrics.
5. eval-agent KPIs: Actualizar ~/ai-lab/agent-eval/kpis/erudito.yaml con los nuevos endpoints y probes.

Decisiones de diseno

  • Docker, no bare metal: v2 corria directo como proceso Python. v3 va en container para consistencia con el resto del mesh y facilidad de restart/update.
  • Repos montados read-only: Erudito lee los repos pero nunca los modifica. El auto-enrich de metadata genera el frontmatter en memoria, no escribe en el repo original.
  • Misma red que LiteLLM: Ya existe, ya tiene acceso a Qdrant, Redis, Ollama, y NotebookLM MCP. No creamos red nueva.
  • Sanitizer como compose service: Se despliega junto con Erudito pero es independiente. Si Erudito se reinicia, el sanitizer sigue corriendo y viceversa.
  • Backward compatible: Los endpoints que existen hoy siguen funcionando. eval-agent no se rompe durante la migracion.
