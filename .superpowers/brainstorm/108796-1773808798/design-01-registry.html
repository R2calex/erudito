Seccion 1/6 — El Registry (Mapa Central)

El corazon de Erudito v3. Todo gira alrededor de este registro.

Que es

Un archivo YAML (data/registry.yaml) que mapea cada proyecto del AI-Lab a su notebook de NotebookLM y su repo de GitHub. Es la unica fuente de verdad para saber: que proyectos existen, donde viven, y en que estado estan.

Estructura de una entrada

data/registry.yaml
projects: infra-mcp: path: ~/ai-lab/infra-mcp node: hanzo repo: r0calex/infra-mcp # GitHub notebook_id: null # Se llena al crear notebook last_hash: e2c8bfc... # Ultimo commit procesado last_sync: 2026-03-17T14:00:00Z status: validated # pending | synced | validated | stale coverage: 0.85 # KPI: % de docs indexados y validados auto_enriched: false # true si metadata fue inferida doc_count: 12 # .md files tracked last_nlm_session: 2026-03-17T10:00:00Z # Ultima consulta a NotebookLM

Ciclo de vida de un proyecto en el registry

Estados y transiciones
pending
──registro──▶
synced
──rondin OK──▶
validated
validated
──nuevo commit──▶
stale
──re-sync──▶
validated
pending: Proyecto registrado, sin notebook ni indexacion
synced: Archivos en Qdrant + fuentes en NotebookLM, pero sin validar
validated: Rondin completo: Qdrant + NotebookLM + preguntas respondidas + notas creadas
stale: Hay commits nuevos que no se han procesado

Operaciones del Registry

register(name, path, node, repo) → Agrega proyecto con status=pending
get(name) → Retorna la entrada completa
update_sync(name, hash, notebook_id) → Actualiza hash, sync time, status=synced
mark_validated(name, coverage) → status=validated con KPI de cobertura
mark_stale(name) → Cuando se detecta nuevo commit sin procesar
list_by_status(status) → Filtrar por estado (util para el rondin)
summary() → KPI global: total, por estado, cobertura promedio

Decisiones de diseno

  • YAML no DB: Es un archivo plano. Con 10-20 proyectos no necesitamos Postgres para esto. Facil de leer, editar manualmente, y versionar en git.
  • notebook_id nullable: Un proyecto puede existir sin notebook (si NotebookLM no esta disponible). Erudito sigue funcionando con Qdrant.
  • coverage como campo: Permite que eval-agent lea el registry directamente para el KPI de cobertura sin llamar a Erudito.
