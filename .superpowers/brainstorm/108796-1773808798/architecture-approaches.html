Erudito v3 — Propuestas de Arquitectura

3 enfoques con diferentes trade-offs. Todos cumplen los mismos requisitos funcionales.

Resumen de requisitos acordados

✓ Mapa triple: proyecto + notebook_id + repo (1:1)
✓ Event-driven por deltas (hash comparison)
✓ Auto-enrich metadata faltante + hook de enforcement
✓ Sanitizer local en Hanzo (fork de kubo-sanitizer)
✓ Query: Qdrant primero, NotebookLM si score < umbral
✓ "No se" honesto cuando no hay info
✓ Sin alertas al mesh por ahora (solo log interno)
✓ KPIs: coherencia (vs NotebookLM) + cobertura (proyectos validados)
✓ mesh-overview notebook en backlog (fase 2)
A

Monolito Refactoreado

Un solo main.py como hoy, pero reescrito con la nueva logica. Erudito v2 evoluciona a v3.

Estructura:
erudito/
  main.py         # FastAPI + todo el core
  notebooklm.py   # Cliente NotebookLM MCP
  sanitizer.py    # Cliente sanitizer
  registry.py     # Mapa proyecto-notebook-repo
  data/           # Estado local

Pros

  • Menor cambio vs v2
  • Facil de debuggear (un proceso)
  • Deploy simple

Cons

  • main.py crece mucho
  • Dificil de testear en aislamiento
  • Mezcla responsabilidades
B

Modular por Dominio

Erudito se divide en modulos con responsabilidades claras. Un proceso, multiples archivos bien separados.

Estructura:
erudito/
  main.py           # FastAPI app + endpoints
  core/
    registry.py     # Mapa triple (proyecto+nb+repo)
    scanner.py      # Delta detection (git hashes)
    indexer.py      # Qdrant embedding pipeline
    query.py        # Search + confidence routing
  integrations/
    notebooklm.py   # Cliente NotebookLM MCP
    sanitizer.py    # Cliente sanitizer Hanzo
    github.py       # Repo sync (opcional)
  data/             # registry.yaml, audit.jsonl
  kpis/             # KPI definitions para eval-agent

Pros

  • Cada modulo testeable por separado
  • Facil agregar integraciones (github, mesh-overview)
  • Responsabilidades claras
  • Un solo proceso, un solo deploy

Cons

  • Mas archivos que manejar
  • Rewrite mas grande que A
C

Microservicios Separados

Cada responsabilidad es un servicio independiente con su propio container. Se comunican via HTTP/Redis.

Servicios:
erudito-api       # FastAPI gateway (:8095)
erudito-scanner   # Delta watcher + sync
erudito-indexer   # Qdrant pipeline
erudito-nlm       # NotebookLM orchestrator
sanitizer-hanzo   # Masking service

Pros

  • Maximo aislamiento
  • Escala independiente
  • Si NotebookLM se cae, nada mas se afecta

Cons

  • 5 containers = mas complejidad ops
  • Overhead de red entre servicios
  • Mas dificil de debuggear
  • Overkill para el volumen actual

Recomendacion: B (Modular por Dominio)

A repite el problema de v2 — main.py monolitico que crece sin control.
C es overkill — no tenemos el volumen para justificar 5 containers, y agrega complejidad ops innecesaria.
B es el sweet spot: un solo proceso facil de operar, pero con modulos claros que se pueden testear, extender y entender por separado. Agregar mesh-overview despues es un archivo nuevo en integrations/, no un rediseno.
